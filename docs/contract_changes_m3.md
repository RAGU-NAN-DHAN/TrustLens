# Contract changes proposed by M3

The team has to agree on these before M1 and M2 code against them. Everything else follows the plan in `TrustLens_Context.md`.

| Where | Change | Why |
|---|---|---|
| `Evidence` | add `highlight_span` (`{start, end}` or null) and `highlight_score` | Evidence highlighting marks the passage sentence that matches the claim |
| `ClaimDecision` | add `correction_verified` (bool or null) and `correction_support_score` | Correction checker result. The UI hides a correction that isn't backed by the evidence |
| `ClaimDecision` | `self_consistency_score` and `evidence_relevance_score` may be null | M3 can produce decisions before M1 and M2 fill these in |
| `VerificationResult.verifier` | values are `"gemini"` and `"groq_qwen"` (was `"llama_groq"`) | Verifier 2 must not be Llama, which wrote the answer |
| `VerificationResult.model_version` | the Gemini verifier is `gemini-2.5-pro` (the plan's example said flash) | Matches the deck |
| `AnalysisResult` (the `/analyze` response) | add `question`, `answer_text`, `evidence` (flat list, linked by `claim_id`) and `created_at` | The UI needs the answer text to colour it and the evidence to show it |
| New route | `GET /api/v1/history` returns a list of `HistoryItem` (`answer_id`, `question`, `trust_score`, `claim_count`, `created_at`) | History page |
| Rule | the disagreement rule decides `final_verdict`; M1's fusion only adds the trust score | One owner for the verdict |

## M3 functions M2's pipeline calls

```python
from app.services.verification import verify_claim        # verify_claim(claim_text, evidence, verifier, mock=None, claim_id=None) -> dict
from app.services.disagreement import resolve_disagreement # resolve_disagreement(results) -> dict
from app.services.correction import write_correction, check_correction
from app.services.highlighting import highlight_evidence   # highlight_evidence(claim_text, evidence) -> list[dict]
```

Order per claim: `highlight_evidence` → `verify_claim` ×2 → `resolve_disagreement` → if contradicted, `write_correction` then `check_correction`. `backend/scripts/demo_m3.py` shows the exact wiring, including what to do when a verifier fails (unverifiable + needs review, never a guessed verdict).
